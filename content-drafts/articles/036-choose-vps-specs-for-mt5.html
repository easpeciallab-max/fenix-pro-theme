การเลือก สเปก VPS สำหรับ MT5 ไม่ควรเริ่มจากแพ็กเกจที่เขียนว่า “รองรับ EA” เพียงอย่างเดียว เพราะ Workload ต่างกันมากตามจำนวน Terminal, Chart, Symbol, Indicator, ความถี่ Tick, EA Logic และงาน Backtest สเปกที่เพียงพอกับ EA หนึ่งตัวอาจค้างเมื่อรันหลายบัญชีหรือเปิด Market Watch จำนวนมาก

วิธีที่แม่นกว่าคือกำหนด Workload เป้าหมาย เลือกเครื่องที่มี Headroom แล้ว Load Test ด้วยชุดงานจริงก่อนย้ายเงินทุน ทั้ง CPU, RAM, Disk, Network และระบบปฏิบัติการต้องผ่านพร้อมกัน เพราะคอขวดเพียงจุดเดียวทำให้ EA รับ Tick หรือส่งคำสั่งไม่ทันได้

สารบัญ

  • เริ่มจากรายการ Workload
  • เลือก CPU อย่างไร
  • วาง RAM และ Page File
  • SSD และพื้นที่เก็บข้อมูล
  • Network และ Location
  • Windows และสิทธิ์ใช้งาน
  • Load Test ก่อนใช้งานจริง

เขียนรายการ Workload ก่อนเทียบราคา

ข้อมูล สิ่งที่ต้องจด
Terminal จำนวน MT5 ที่เปิดพร้อมกันและจำนวนบัญชี
Charts จำนวนกราฟ, Symbol, Timeframe และ Indicator ต่อกราฟ
EA จำนวน Instance, ความถี่คำนวณ, File/Network I/O และ Dashboard
Data จำนวน Symbol ใน Market Watch, History/Tick ที่ต้องเก็บ
Operations Antivirus, Monitoring, Backup และการ Remote เข้าเครื่อง

แยก Production Trading ออกจาก Backtest/Optimization หากทำได้ Strategy Tester แบบหลาย Agent สามารถใช้ CPU และ RAM สูงเป็นช่วงยาว การรันพร้อม Terminal ที่ส่งคำสั่งจริงทำให้ Latency และความเสถียรแย่โดยไม่จำเป็น

CPU: ดูความเร็วต่อ Core และโหลดพร้อมกัน

EA บน Chart หนึ่งมักประมวลผล Event ตามลำดับของ Instance นั้น จึงไม่ควรดูจำนวน vCPU อย่างเดียว ความเร็วต่อ Core, CPU Generation, Steal/Ready Time ในระบบ Virtualization และการ Oversubscribe ของผู้ให้บริการมีผลต่อเวลาประมวลผล

คำถามที่ควรถามผู้ให้บริการ:

  • vCPU เป็น Shared, Burstable หรือ Dedicated
  • มี Fair-use/CPU Throttling หลังใช้ต่อเนื่องหรือไม่
  • แจ้งรุ่นหรืออย่างน้อย Generation ของ CPU หรือไม่
  • ปรับขนาดเครื่องโดยไม่เปลี่ยน IP/ล้าง Disk ได้หรือไม่
  • มีกราฟ CPU ต่อเนื่องและ Alert หรือไม่

ถ้า Terminal หลายตัวทำงานพร้อมกัน Multi-core ช่วยกระจาย Process ได้ แต่ EA หนักหนึ่ง Instance ไม่ได้เร็วขึ้นเป็นสัดส่วนกับจำนวน Core เสมอ ต้องวัด Peak CPU ตอน Session เปิด ข่าวแรง และตอน Terminal Sync History

RAM: เผื่อ Working Set ไม่ใช่ดูตอนเปิดใหม่

MT5 ใช้ RAM เพิ่มตามกราฟ ข้อมูลราคา Indicator, EA, Report และ Cache Windows การเปิด Terminal ใหม่แล้วดู Task Manager ทันทีอาจประเมินต่ำ เพราะ History ยังโหลดไม่ครบและ EA ยังไม่เข้าสภาวะตลาดที่มี Tick หนาแน่น

แนวทางวาง RAM:

  1. เปิด Workload เป้าหมายทั้งหมด
  2. ปล่อยให้ Sync History และทำงานผ่าน Session สำคัญ
  3. วัด Working Set และ Commit Charge สูงสุด
  4. เผื่อ Windows, Antivirus, Update และ Remote Session
  5. เพิ่ม Headroom สำหรับ Terminal Restart/Update ที่ Process ซ้อนชั่วคราว

หากระบบเริ่มใช้ Page File หนัก Disk Latency จะเพิ่มและ Terminal อาจตอบสนองช้า ไม่ควรแก้ด้วยการปิด Page File แบบเหมารวม แต่ควรเพิ่ม RAM/ลด Workload และตั้ง Monitoring ให้เห็น Memory Pressure

SSD, IOPS และพื้นที่ว่าง

MT5 เขียน Log, History, Tick, Cache และ Tester Data ต่อเนื่อง หลาย Terminal ทำให้ Random I/O เพิ่ม เลือก SSD ที่มีประสิทธิภาพสม่ำเสมอและมีพื้นที่ว่างสำหรับ Update/History ไม่ใช้ Disk จนเกือบเต็ม

  • แยกโฟลเดอร์แต่ละ Terminal ให้ชัด
  • กำหนดนโยบายเก็บ Log และ Archive แทนการลบโดยไม่ตรวจ
  • ไม่ Sync โฟลเดอร์ Data ที่กำลังใช้งานด้วยเครื่องมือซึ่ง Lock File
  • สำรอง Preset, Profile และไฟล์ตั้งค่า แต่อย่าถือ Snapshot เป็น Monitoring
  • ตรวจ Disk Queue/Latency ไม่ดูเพียงเปอร์เซ็นต์พื้นที่

Network: ใกล้ Broker Server สำคัญกว่าคำว่า “เร็ว”

Bandwidth ที่มากไม่ได้รับประกัน Latency ต่ำ VPS ควรอยู่ใกล้ Trading Server ของ Broker ในเชิงเส้นทาง Network และมี Packet Loss/Jitter ต่ำ การวัดต้องทำจาก VPS ไปยัง Server เป้าหมาย ไม่ใช้ผล Speed Test ไปศูนย์ข้อมูลสุ่มแทน

ตรวจ:

  • Average และ Tail Latency ในหลายช่วงเวลา
  • Jitter และ Packet Loss
  • Route เปลี่ยนในช่วง Peak
  • Network Redundancy และ SLA ของผู้ให้บริการ
  • ระบบแจ้งเหตุและช่องทาง Support

อ่านภาพรวมเพิ่มเติมที่ VPS สำหรับ EA คืออะไร และทดสอบ Latency จาก VPS ไปยัง Trading Server จริงก่อนตัดสินใจเลือก Region

Windows, License และสิทธิ์

ตรวจว่า Image Windows ยังได้รับ Security Update, License ถูกต้อง และรองรับ MT5/เครื่องมือ Remote ที่จะใช้ เลือกภาษา/Timezone ให้ทีมเข้าใจ แต่ Logic EA ควรยึด Broker Server Time ตามที่ออกแบบ ไม่ใช้ Windows Clock แบบไม่ตรวจ

ไม่ควรปิด Windows Update ถาวรเพื่อเลี่ยง Restart ให้กำหนด Maintenance Window, Active Hours, Backup และขั้นตอนตรวจหลัง Patch แทน บัญชี RDP ต้องใช้รหัสผ่านเฉพาะที่แข็งแรง จำกัดผู้มีสิทธิ์ และไม่แชร์บัญชี Administrator โดยไม่มี Audit

Load Test และ Acceptance Checklist

ก่อน Production ให้ติดตั้งตาม คู่มือติดตั้ง FENIX PRO EA และรัน Demo ด้วยโครงจริง:

  1. เปิด Terminal/Chart/EA ครบตามจำนวนสูงสุดที่วางแผน
  2. Sync History และเปิด Monitoring CPU, RAM, Disk, Network
  3. ทดสอบช่วง Session เปิดและช่วง Tick หนาแน่น
  4. Restart VPS แล้วตรวจ Auto-start, Login, AutoTrading และ EA State
  5. Disconnect RDP แล้วตรวจว่า Process/Log ยังเดิน
  6. จำลอง Disk ใกล้เต็ม, Network ขาดช่วง และ Terminal ค้าง
  7. วัดต่อเนื่องหลายวันก่อนอนุมัติ Production

เกณฑ์ผ่านควรเขียนเป็นค่าที่วัดได้ เช่น CPU/RAM Headroom ขั้นต่ำตามนโยบายทีม, ไม่มี Memory Pressure, Disk Latency ไม่พุ่งต่อเนื่อง, Terminal รับ Tick/เขียน Log ปกติ และ Alert ส่งถึงผู้รับผิดชอบ

สรุปการเลือกแพ็กเกจ

  • EA/Terminal น้อยและ Logic เบา: เริ่มจากแพ็กเกจเล็กที่ปรับเพิ่มได้แล้ววัดจริง
  • หลาย Terminal/หลาย Chart: ให้ความสำคัญกับ RAM, Core และ Disk I/O
  • Scalping/Execution-sensitive: ให้ความสำคัญกับ Location, Jitter และ Broker Route
  • Backtest/Optimization: แยกจาก Production หรือจัด Maintenance Window
  • งานสำคัญ: เลือก Monitoring, Backup, Support และ Recovery มากกว่าสเปกกระดาษ

สรุป: ไม่มีสเปก VPS ชุดเดียวที่เหมาะกับ EA ทุกตัว เลือกจาก Workload ที่ระบุได้ วัด Peak จริง เผื่อ Headroom และมีแผนขยาย/กู้คืน จึงจะลดความเสี่ยงจากเครื่องที่ดูพอในวันปกติแต่ล้มในเวลาสำคัญ

คำเตือนความเสี่ยง: VPS ช่วยเพิ่มความต่อเนื่องของระบบ แต่ไม่รับประกันการเชื่อมต่อ การส่งคำสั่ง หรือผลการเทรด ผู้ใช้ต้องติดตามสถานะและมีแผนรับเหตุขัดข้อง การใช้ EA และผลิตภัณฑ์ที่มี Leverage มีความเสี่ยงสูง อ่าน คำเตือนความเสี่ยงฉบับเต็ม
