VPS ที่รัน MT5 เปิดออนไลน์ต่อเนื่อง มี Credential, EA และข้อมูลการเทรด จึงต้องดูแลเหมือนระบบ Production ไม่ใช่คอมสำรอง การรักษาความปลอดภัยต้องครอบคลุมบัญชีผู้ใช้ Remote Access, Windows Update, Firewall, ไฟล์, Backup, Monitoring และขั้นตอนเมื่อสงสัยว่าถูกเข้าถึง

เป้าหมายไม่ใช่ปิดทุกอย่างจน EA ใช้งานไม่ได้ แต่ลด Attack Surface ตามหลัก Least Privilege และเปลี่ยนแปลงผ่าน Maintenance Window ที่ทดสอบได้ ไม่ปิด Security Control แบบถาวรเพื่อหวังลด Latency หรือหลีกเลี่ยง Restart

สารบัญ

  • บัญชีและรหัสผ่าน
  • รักษาความปลอดภัย RDP
  • Update โดยไม่ทำ Production ล่ม
  • ป้องกันไฟล์ EA และข้อมูลลับ
  • Backup และ Restore Test
  • แผนเมื่อสงสัยว่าถูกบุกรุก

บัญชี Windows และ Credential

  • ใช้รหัสผ่านยาว ไม่ซ้ำกับ WordPress, Email, Broker หรือบริการอื่น
  • เก็บใน Password Manager ที่เชื่อถือได้ ไม่ส่งในแชต/ไฟล์ข้อความ
  • เปลี่ยนชื่อ/ปิดบัญชีที่ไม่ใช้และทบทวนสมาชิก Administrators
  • สร้างบัญชีแยกสำหรับงานประจำ ลดการใช้สิทธิ์ Administrator
  • ไม่แชร์บัญชีเดียวหลายคนโดยไม่มี Audit
  • เปิด MFA ผ่าน RD Gateway/VPN/Provider Control Plane เมื่อรองรับ

หากผู้ให้บริการมี Console, Snapshot และ Rebuild ผ่าน Portal บัญชี Provider ต้องเปิด MFA ด้วย เพราะผู้ที่ยึด Portal ได้อาจเข้าถึงหรือทำลาย VPS แม้รหัสผ่าน Windows แข็งแรง

ลดการเปิด RDP สู่ Internet

การเปิด RDP โดยตรงให้ทุก IP เพิ่มโอกาสถูก Scan/Brute-force แนวทางที่แข็งแรงกว่าคือใช้ Provider Firewall/Security Group จำกัด Source IP, VPN หรือ RD Gateway ตามขนาดระบบ พร้อมเปิด Network Level Authentication (NLA) เมื่อ Environment รองรับ

Checklist:

  1. จำกัด Inbound ให้เฉพาะ Port/Source ที่จำเป็น
  2. ไม่ปิด Windows Firewall ทั้งระบบ
  3. ใช้ NLA/TLS และตรวจ Certificate Warning ก่อนส่ง Credential
  4. ปิด Drive/Clipboard/Printer Redirection ที่ไม่จำเป็นเพื่อลด Data Transfer Risk
  5. ตรวจ Failed Logon/Event Log และตั้ง Alert
  6. กำหนด Session Limit โดยไม่ทำให้ MT5 ถูก Log off โดยไม่ตั้งใจ

การเปลี่ยน Port RDP อาจลด Noise จาก Scan บางส่วน แต่ไม่ใช่ Authentication หรือ Firewall Control และไม่ควรถูกนับเป็นมาตรการหลัก

Patch โดยมี Maintenance Runbook

Windows, MT5 และเครื่องมือ Remote ต้องได้รับ Security Update แต่ Production Trading ต้องวางแผนเวลา Restart:

  • กำหนด Maintenance Window นอกช่วงที่ระบบมี Open Risk เมื่อทำได้
  • อ่าน Release/Provider Notice และสำรองก่อนเปลี่ยนสำคัญ
  • ทดสอบ Update บน Staging/เครื่องสำรองหากระบบมีหลายบัญชีสำคัญ
  • ตั้ง Active Hours/Restart Policy ให้สอดคล้องกับ Runbook
  • หลัง Restart ตรวจ Auto-start, Account, Server, EA, Preset และ Log
  • เก็บ Change Log พร้อมวัน เวลา และผู้ดำเนินการ

อย่าปิด Update ถาวร เพราะช่องโหว่สะสมทำให้ Recovery ยากขึ้น อ่าน ตั้ง MT5 เปิดอัตโนมัติหลัง Restart และทดสอบทุกครั้งหลัง Patch

ไฟล์ EA, Preset และข้อมูลบัญชี

ดาวน์โหลดจากแหล่งที่ยืนยันได้

เก็บ Original Package, Version และ Checksum ของ EA/Installer ไม่เปิดไฟล์ EXE, Script หรือ DLL จากลิงก์ที่ไม่ยืนยัน แม้ส่งมาจากบัญชีคนรู้จัก เพราะบัญชีอาจถูกยึด

จำกัด DLL/WebRequest

เปิด Allow DLL Imports หรือ WebRequest เฉพาะ EA ที่จำเป็นและ Domain ที่ยืนยัน ตรวจ Documentation ว่าข้อมูลใดถูกส่งออก ไม่อนุญาตแบบกว้างเพียงเพื่อให้ Error หาย

ไม่เก็บ Password แบบ Plain Text

หลีกเลี่ยงการใส่ Login/รหัสผ่านใน Preset, Script, Note หรือชื่อไฟล์ จัด Permission ของโฟลเดอร์และ Backup ให้เฉพาะผู้รับผิดชอบ

แยก Production และ Download

ไม่ใช้ VPS Trading เป็นเครื่องท่องเว็บทั่วไป ดาวน์โหลดไฟล์ หรือเปิด Email ลด Browser/Plugin และ Software ที่ไม่จำเป็นเพื่อลด Attack Surface และ Resource Noise

Backup ต้องกู้คืนได้ ไม่ใช่แค่มี Snapshot

แยกสิ่งที่ต้องสำรอง:

ข้อมูล วิธีปฏิบัติ
Inventory/Runbook เก็บนอก VPS และมี Version History
EA/Preset/Profile เก็บ Package ที่ตรวจ Checksum และ Version
Logs/Reports ส่ง/สำรองตาม Retention โดยไม่รวม Secret
VPS Image/Snapshot ใช้สำหรับ Recovery เร็ว แต่แยกจาก Account เดียวกันเมื่อทำได้
Credentials เก็บใน Password Manager ไม่ฝังใน Backup ที่เปิดอ่านง่าย

ใช้หลักหลายสำเนา หลายสื่อ และมีสำเนาแยก/แก้ไขไม่ได้ตามความเหมาะสม เพราะ Ransomware อาจโจมตี Backup และเอกสารกู้คืนด้วย ทดสอบ Restore ลง VPS ใหม่เป็นรอบ จับ Recovery Time และตรวจ EA Version/State หลัง Restore

Monitoring และ Audit

  • Power/Uptime และ Provider Incident
  • Failed/Successful Logon ที่ผิดเวลา
  • Process Count และไฟล์ EA เปลี่ยน Checksum
  • CPU/RAM/Disk/Network ผิดปกติ
  • Heartbeat, Connection และ Journal Error
  • Windows/MT5 Update และ Scheduled Task เปลี่ยน

Alert ต้องไปช่องทางนอก VPS และมี Severity/ผู้รับผิดชอบ หากทุกหลักฐานอยู่ในเครื่องเดียว เมื่อเครื่องถูกยึดหรือลบจะไม่มีข้อมูลตรวจสอบ

เมื่อสงสัยว่าถูกเข้าถึง

  1. ประเมิน Open Position และทำตาม Risk/Emergency Runbook
  2. จำกัด Network/Account ผ่าน Control Plane ที่เชื่อถือได้
  3. เก็บ Snapshot/Log/เวลา ก่อนลบหรือ Rebuild หากนโยบายอนุญาต
  4. เปลี่ยน Credential จากอุปกรณ์สะอาด รวม Provider, Email และ Trading Account
  5. ตรวจ Broker Activity, Withdrawal Setting และ Session
  6. Rebuild จาก Image/Package ที่เชื่อถือได้ ไม่มั่นใจแล้วใช้งานต่อ
  7. ทำ Root-cause Review และปิดช่องโหว่ก่อน Resume

อย่าพยายาม “ทำความสะอาด” เครื่องที่ไม่เชื่อถือแล้วและเปิด Production ต่อโดยไม่มีหลักฐานว่าปลอดภัย การ Rebuild มักตรวจสอบง่ายกว่าการเดาว่า Malware ถูกลบหมดหรือไม่

ดู Runbook ระบบขัดข้องที่ วิธีแก้ VPS/MT5/EA ทีละจุด และวาง Headroom ตาม สเปก VPS สำหรับ MT5

สรุป: ความปลอดภัย VPS เป็นงานต่อเนื่อง: ลดช่องทางเข้า แยกสิทธิ์ อัปเดตเป็นรอบ ตรวจไฟล์/เหตุการณ์ และกู้คืนจากสำเนาที่เชื่อถือได้ การตั้งครั้งเดียวแล้วไม่ติดตามไม่เพียงพอสำหรับเครื่องที่ออนไลน์ตลอด

คำเตือนความเสี่ยง: ไม่มีมาตรการใดรับประกันความปลอดภัยหรือ Uptime ได้ 100% VPS และซอฟต์แวร์อาจถูกโจมตีหรือขัดข้อง ผู้ใช้ต้องติดตามบัญชีและมีแผนสำรอง การเทรดมีความเสี่ยงสูง อ่าน คำเตือนความเสี่ยงฉบับเต็ม
